# Does a fight batch really read 75 GB? (2026-11-04)

Question (housekeeping): the lab runner's log line for the 00:51:16Z fight batch, `batch-00/scen-00: rc=0 in 542.8s cpu=3912.4s reads=2655580 read_mb=75863.4`, says 75 GB was read in nine minutes. Is that disk traffic or the file cache answering? Read-only; the samples are in `logs/fight-batch-reads/now/samples.csv` (not committed). No fix proposed.

**It is the file cache, not the disk.** The lab computes `read_mb` from the Windows Job Object its runner gives each command (`tools/lab/winsys.py`, `accounting()`; `tools/lab/runner.py`, `accounting_fields()`): the job's I/O counters, `ReadTransferCount` divided by 1e6, summed over every process that has run in the job, children included, and `reads` is the matching read-operation count. Those counters are the I/O manager's: every completed read request counts, whether the bytes came from the disk or from the system file cache, and pipe and network reads count too; they say what the processes asked for, not what the disk delivered. A fight batch is `referee/scenarios.py` driving 50 fights through 8 servers on the real game (`referee/game-lab`, 2.9 GB: the `.pck` 1.9 GB, the `.exe` 0.9 GB), so each batch launches the game over and over, and the game reads its own files at every launch. To compare, I sampled the counters every 5 s (`Get-Counter` on `\PhysicalDisk(*)\Disk Read Bytes/sec` and `\Process(*)\IO Read Bytes/sec`, errors silenced) over the last 140 s of the next batch that ran, `batch-02/scen-02` of job 20261104T0207-fights (02:33:41 to 02:36:04Z; the batch ran 02:26:04 to 02:35:54Z, 590.7 s, 56,892.8 MB by the runner's count, 96.3 MB/s on average, the same kind of batch as the 00:51Z one, which ended before I could sample it, and I did not catch the first 76% of this one). In that window the physical disks read **187 MB in all** (D: 161 MB, C: 26 MB), a mean of **1.3 MB/s** and a peak of 5.0 MB/s, while the game processes (`slaythespire2`) read **11,834 MB through the process counters, a mean of 85 MB/s** (the batch's own mean was 96 MB/s, and a process that starts and ends between two samples is missed, so the sampler's figure is a floor): about **63 times** what the disk delivered, so over the whole batch about 0.8 GB of disk reads against 56.9 GB counted, or roughly 1.4% of the counted bytes; the same ratio on the 75.9 GB batch would be about 1.1 GB. The counted bytes per fight are 56,893 MB / 50 fights = 1.1 GB, about the size of the game's `.exe` plus part of its `.pck`, which fits one launch per fight reading its files from the cache (that is an inference from the sizes, not a measurement of which files). One more reader showed up that the lab's figure does not include: Windows Defender (`MsMpEng`) read 60,673 MB through the process counters in the same 140 s, a mean of 433 MB/s, again from the cache (the disks stayed at 1.3 MB/s), presumably scanning what the game launches. So the 75 GB is neither a disk load nor a sign that the batch is disk-bound (D: read 1.2 MB/s while the batch ran at 3,900 CPU seconds in 540 s); `read_mb` and `reads` in `runner.log` and in the clock report (`tools/lab/clock_report.py`) are bytes and calls requested of the file cache, not disk traffic. One consequence to check, not done here: `2026-11-02-disk-bound.md` tells cold runs of a step from warm ones partly by this `read_mb` (its rule (a), 300 MB or more against under 100 MB), which counts cache hits as reads, while its machine-wide figure (199.6 GB in 26 hours) came from the watcher's disk counters and is not affected.
